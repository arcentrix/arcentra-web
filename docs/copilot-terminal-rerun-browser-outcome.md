# Terminal rerun browser outcome acceptance client

This opt-in acceptance client observes real browser/API/command/output evidence. Offline contract tests do not establish a browser or runtime acceptance result. The backend fixture owns activation, its original enclosing deadline, and independent durable/runtime/S3/replay/cleanup checks.

## Minimal integration

Use two bounded invocations of the existing actual-backend Node/browser harness, with the same production loopback router, Redis-backed login and process-group cleanup. No test-only HTTP routes, seeded sessions or synthetic execution records are needed. The Go fixture owns the enclosing deadline and independent durable/runtime/S3 assertions.

1. Go creates the original through the authenticated production manual trigger and real definition loader/prospective snapshot capture. Freeze source SHA, definition revision, parsed spec, commands, variables and one UTC cutoff before capture. Real independent approvals allow the original shell to fail with exit 23 and exhaust its bounded attempts. Require original Run FAILED (4), Job FAILED (5), every used shell failed before cutoff, no artifact, cleanup complete. Retain the original durable baseline. Poll until the fixed cutoff before starting the new intent; never move cutoff or modify source/variables.
2. Phase A is the already committed `runRerunBrowserPreparation` and its exact ten-field contract. Real requester login; eligibility is read-only; one Prepare fixes RequestID; explicit unchecked consent then one Confirm. Its `confirmed-awaiting-independent-approval` result is intermediate only. On an uncertain Prepare/Confirm, recovery keeps RequestID/IntentID and only inspects; no fresh Prepare/Confirm is permitted. A response-loss variant must use separate truthful counters. The normal preparation helper fails closed on transport loss; it does not retry a mutation.
3. Go verifies the confirmed tuple, exact snapshot/source/spec bindings and zero votes by requester. The production sealed reference dispatcher, real Agent claim and controlled preparation must create a new approval. Require distinct Run/Job/Step/Claim/Approval identities, exact prepared checkout, no command starts and no output. Go sends the first candidate's real authorized service vote, verifies one of two approvals and still zero commands. Do not create decisions by SQL or fabricate a queue payload.
4. Phase B is `runRerunBrowserOutcome` in `tests/copilot-rerun-outcome-journey.mjs`. Start a fresh real browser login as the second candidate (distinct from requester and first candidate). It verifies exact pending approval evidence, deliberately checks the existing retry-plan acknowledgement, and sends one real UI approval. It then inspects fresh evidence, waits for the exact new run/job/step success and source/log proof, and uses the existing artifact page and download button to compare actual bytes with the frozen expected size/SHA256. It re-reads the original and requires FAILED with its original step identities and zero artifacts.
5. Go independently checks the actual Decision rows (the public approval DTO has no DecisionID), old baseline unchanged, same captured commands/variables/source/spec, exact new claim/terminal receipts and first-generation success, lifecycle Start/Exec counts, and actual S3 object/registration/hash/size/producer identity. Replaying exact original Confirm after terminal must preserve IDs/timestamps and must not increase dispatch, claim, start, exec or upload counts. Audit all owned cleanup. Only this full Go check plus the browser diagnostics allows overall acceptance.

A time-dependent shell is intentional: captured inputs remain unchanged; external clock changes. This proves immutable-input rerun execution, not deterministic reproducibility. The fixed UTC threshold and both real outcomes belong in acceptance evidence. No branch/source mutation is required by this journey.

## Phase B input

`version: copilot-terminal-rerun-outcome-browser-v1`; exact schema is enforced by `validateOutcomeContract` (unknown fields fail).

- `scope`: unchanged Phase A ten-field contract. `scope.actorId` is requester; full definition/source SHA and spec/snapshot digests are mandatory.
- `actorId`, `firstApproverId`: two distinct operator-selected candidates, both different from requester.
- `deadlineUnixMilli`: remaining original Go deadline, never a new duration. Child process timeout is capped by this deadline; final vote must also precede `target.approvalExpiresAtUnixMilli`.
- `fixedTime`: `cutoffUnixMilli`, `originalFinishedAtUnixMilli`, from the frozen fixture and actual terminal receipt. Original completion must be strictly before cutoff. Phase B must start at/after cutoff.
- `original`: `claimId`, `approvalId`, `stepRunIds` from actual terminal rows. Full old row/decision baseline remains Go-owned, rather than passing raw protected state through the browser.
- `target`: `requestId`, `intentId`, `runId`, `jobRunId`, `agentId`, `claimId`, `approvalId`, `evidenceHash`, `approvalExpiresAtUnixMilli`, `steps`. All are read from actual confirmed/gate/claim records. `steps` are exactly the minimal fixture's shell then artifact upload, each `{name,stepIndex,uses,action,attemptRunIds}` with the complete reserved attempt identity list from actual approval evidence. `uses` is `shell` or `builtin:artifacts`; shell action is empty or `run` as actually parsed, and upload action is `upload`. Two through five bounded attempts are accepted; this fixture should use two. None of these fields authorize execution.
- `expectedOutput`: `name`, `size` (1..1 MiB), `sha256`, `logMarker`. Frozen synthetic proof expectations; no S3 credentials, bucket path, URL, commands, variable values, access tokens or cipher material. The artifact ID is discovered from the actual registered new-run list, not invented in advance.

Contract JSON must be <=16 KiB. Both phases reuse existing mandatory actual-browser/real-stack opt-ins, official pinned browser and harness secret guards. Synthetic browser credentials stay only in the already existing private environment channel and never enter the contract/receipt. No provider/model transport is required. Candidate needs the existing scoped project/pipeline/approval read and approval decision grants; artifact list/download already use pipeline read. Do not add broader grants.

## Phase B output and acceptance boundary

A small credential-free receipt reports exact scope/actor/new identity/claim/approval, actual source SHA, terminal status, exact command/upload first-attempt step IDs, marker observation, downloaded artifact ID/size/SHA256, original FAILED checks, one approval POST and one artifact download. It always has `runtimeAcceptanceComplete: false`: this process cannot independently certify Go DB/lifecycle/S3 observations, replay or cleanup. `browserOutcomeComplete: true` means only the actual browser phase finished all its own observations.

The Go caller must separately verify all durable evidence and exact receipt identities. Never accept merely `confirmed`, `approved`, a success toast, a returned target ID, a helper boolean, a mocked response or the offline tests. Missing any independent assertion is a failure, not a skipped optional check.

## Deadlines and uncertainty

Two short subprocesses avoid an additional test coordination server and give the Go fixture a precise first-vote/zero-command checkpoint. Use `min(parent remaining, phase budget)` for each subprocess; never reset the 7-minute fixture or 25-minute hosted hard limit. Cutoff waiting occurs before the new approval exists. Approval expiry is taken from the actual gate and is never extended. A lost approval HTTP response causes only existing UI refresh/inspection, never another vote. A malformed/contradictory response is a failure. Browser polling is read-only and bounded by the original deadline; expiry or forbidden scope is not success. Do not use retries to conceal extra Prepare, Confirm, vote, dispatch, start or upload operations.

## Inert entry point

`tests/actual-rerun-browser.mjs` reuses the existing frontend modules. Launch Node with cwd equal to explicit absolute `ARCENTRA_COPILOT_BROWSER_CWD`. The trusted CI workflow must set `ARCENTRA_COPILOT_BROWSER_FRONTEND_COMMIT` to the exact published frontend checkout pin (40 lowercase hex characters). This is separate from the pipeline source commit and must never be derived from the current HEAD. The wrapper compares actual Git HEAD and clean status against that pin before importing the browser harness and again after the journey, then records the actual readback as `frontendCommit`. Missing, malformed, mismatched or dirty provenance fails closed. Any inherited `UI_TEST_BASE_URL` override, including an empty value, is rejected before browser imports: this client must use the harness-managed Vite server from the verified checkout, never an unrelated loopback server. Keep phase output directories outside this checkout so evidence does not alter its source.

Required existing environment: `ARCENTRA_COPILOT_EXECUTION_BROWSER=1`, `ARCENTRA_REQUIRE_COPILOT_EXECUTION_BROWSER=1`, `ARCENTRA_REAL_STACK=1`, loopback-only `ARCENTRA_ACCEPTANCE_BACKEND_URL`, disposable synthetic `ARCENTRA_ACCEPTANCE_USERNAME` / `ARCENTRA_ACCEPTANCE_PASSWORD`, official browser path from the existing fixture, and distinct absolute `UI_TEST_OUTPUT_DIR` for each phase.

Additional inputs: `ARCENTRA_COPILOT_RERUN_PHASE=prepare|outcome`, `ARCENTRA_COPILOT_RERUN_CONTRACT` (bounded JSON), and `ARCENTRA_COPILOT_RERUN_DEADLINE_UNIX_MILLI` (unchanged enclosing deadline). Outcome contract deadline must equal that environment deadline. The subprocess and browser have at most 45 seconds or remaining parent time, whichever is smaller; the Go caller must retain its existing process-group cancellation and cleanup.

Successful phase files are respectively `copilot-rerun-preparation-receipt.json` and `copilot-rerun-outcome-receipt.json`, <=16 KiB, exclusive mode 0600. They add `frontendCommit` to the helper receipt; no password/session material is written. Before writing either receipt, the wrapper bounded-reads `summary.json` (64 KiB maximum), requires successful actual-backend diagnostics and `frontendServer` witnesses `managed=true`, `mode=vite-development`, `ready=true`, `exitCodeBeforeCleanup=null`, and `signalBeforeCleanup=null`. A failed strict-port child cannot be represented as pinned frontend evidence merely because a different local page answered. This client also opts into the harness managed-child listening witness. Its owned IPC child loads the same Vite configuration/env/proxy semantics, calls `listen` with `strictPort`, and reports the actual bound loopback host/port and PID only after its HTTP server is listening. The harness validates the exact IPC shape, owned PID, origin and live child before any readiness HTTP fetch. Occupied port, malformed witness, startup error/exit or stalled child fails closed. Child exit interrupts the journey; bounded cleanup stops and joins only that owned process. Ordinary harness callers retain their existing CLI behavior. The final summary must also carry `listeningWitness=true`. Run only within the explicitly enabled disposable fixture.
